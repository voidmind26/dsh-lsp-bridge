# 设置 UI 与自动发现设计

## 目标与范围

Web 和 Desktop 共用一个客户端插件。在设置侧栏提供独立「LSP」页面：选择活动会话、扫描语言服务器与运行组件、审阅候选与安装方案、编辑配置并显式保存。界面负责只读诊断与手工配置；安装由智能体显式调用 `lsp_setup` 完成，界面只展示将要执行的确切命令。

## 页面信息架构

- 页面加载后自动做一次诊断与验证（不在界面上宣传这件事，只保留“正在扫描并验证”“来自当前配置”这类状态文案）：先只读诊断，再对“命令与运行组件齐备”的服务器做一次短暂启动（initialize 后立即关闭），因此进入页面就能看到真实的验证状态，不需要先点扫描。验证结果与诊断状态分开标注，不互相覆盖；请求取消即停止后续验证，一次最多验证 4 个。
- 页面分为两个视图：默认「服务器列表」只展示已配置的每个 LSP 及其设置；「新增配置」是独立视图，承载扫描、候选审阅与 JSON 编辑，通过「＋ 新增配置 / ← 返回服务器列表」切换。
- 语言服务器属于项目目录而不是会话：诊断与验证的目标目录取该服务器自己的 `roots`/`workspaceFolders`，没有配置根目录时才用当前会话工作区。卡片直接标注「评估目录：…（来自配置的项目根目录）」，因此配置在其它工程下的服务器也能得到状态与验证，无需切换会话。
- 显式配置在本工作区内的服务器即使项目没有标记文件也会补出状态（按配置本身诊断命令与运行组件），避免列表出现空白；非 catalog 的自定义服务器只做命令层面诊断，不宣称可自动安装。
- 列表页每张卡片展开后显示该服务器的程序路径、启动参数、语言、项目/工作区目录、初始化选项与完整配置，并可一键进入 JSON 编辑；每张卡片同时标注配置状态（可用/缺少运行组件/未安装/未扫描）与验证状态（验证通过/验证失败/未验证），展开后显示验证到的能力、项目根目录或失败原因。
- 新增视图内采用分步分区：选择工作区并扫描 → 审阅服务器候选 → 编辑高级配置 JSON。扫描结果只是建议，加入草稿与保存是两个独立动作。
- 候选以卡片呈现，区分可用、需选择、未安装、缺少运行组件；缺组件时展示原因、依赖状态与确切的安装命令。同时提示可交给智能体执行 `lsp_setup` 自动完成。
- 卡片默认折叠，只显示名称、状态与一行摘要；命令、依赖、安装方案、项目根目录等细节点击展开，并提供「展开全部 / 收起全部」。当前配置的服务器卡片同样折叠，完整配置放在卡片内部的折叠块里。长项目路径列表折叠展示，程序路径允许换行。
- 当前配置优先显示服务器摘要，完整 JSON 放入默认折叠的高级配置，避免初次进入就面对大段代码。
- 保存区域展示未保存状态与不可保存的原因；不把“已配置”误标为“服务器运行中”。保存不做勾选式确认，只在保存区用一行静态提示说明语言服务器不会被 OS 沙箱隔离。
- 样式限定在插件根节点，使用宿主主题变量，支持明暗主题、窄布局、键盘焦点与禁用状态，不引入第二套 UI 框架。

## 宿主契约

- Bundle 保留服务端入口，新增 `exports["./client"]` 与 `dsh.client.platform: web`。
- 浏览器使用 `window.__ModuleLoader__.load` 注册 factory，React 来自宿主；通过 `settingsScope` 和列表型 `settings.section` 注册独立设置页。
- 配置命名空间为 `dsh-lsp-bridge`；UI 保存 `configJson`，Host 在写前解析并校验。配置保存后关闭旧服务池，后续工具调用使用新配置，不自动启动语言服务器。
- UI 使用已有 `settingsScope` 的修订号控制，保存后核对宿主读回值；失败保留草稿。
- 自定义发现接口走 `connection.fetch.register`，不是无认证的裸 HTTP route，因此共享 Web/桌面通信边界。

## 发现接口

路径 `/api/dsh-lsp-bridge/discovery`：

- GET：列出当前已加载会话的 id/cwd，供选择扫描对象。不会为了扫描恢复冷会话。
- POST：只接受 sessionId、refresh 和 languages；服务端从 sessions.get 解析真实 cwd，拒绝客户端提交任意路径或命令。
- 只读扫描不启动任何候选、不运行版本命令、不下载依赖、不修改项目文件。
- 当前沿用 danger-full-access 门控；扫描并不证明语言服务器可信，启用配置前仍需用户确认。

## 扫描与候选

固定目录包含 Go、Rust、TypeScript/JavaScript、Python、C/C++。通用 JSON 配置仍支持其他语言。

从绝对 PATH 目录、常见安装目录和工作区项目固定局部目录检查候选文件。识别 canonical 可执行文件路径，局部候选需要特别审阅。项目扫描不跟随目录符号链接，跳过依赖/构建目录，受深度、目录/项目数量和时间预算限制；截断必须向用户说明。

多个 Go module 默认仍是独立 root，不擅自创建 go.work 或改写依赖关系。发现结果是建议，不直接生效。多候选由用户选择，扫描不安装也不执行候选；安装只在智能体显式执行 `lsp_setup` 时按 catalog 允许列表进行。

诊断阶段同时检查运行组件：语言服务器存在但缺少 SDK（如 `typescript/lib/tsserver.js`）时标记为“缺少运行组件”，界面给出原因，`lsp_setup` 负责安装并用 `initializationOptions` 把 SDK 路径写进配置。

## 构建与验证

客户端使用可读、无 JSX 的 JavaScript 源文件 `src/client.js`，`npm run build:client` 生成 `lib/client.js`，无需额外打包器。运行产物入库，以便 GitHub 源安装不依赖构建脚本。React 是宿主提供的模块，不内联第二份 React。

测试覆盖发现限制、路径边界、配置校验与池替换、认证路由注册契约、会话绑定、客户端加载/草稿和建议转换。模拟宿主测试不等于真实 GUI 安装验收；新增客户端入口需要重新加载插件启动图和刷新现有 GUI，不承诺没有 watcher 时自动热更新。
